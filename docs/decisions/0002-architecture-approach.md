# ADR-0002: 架构方案选型

- 状态: 已接受
- 日期: 2026-06-19
- 决策者: 用户 + ZCode

## 背景

回测引擎有三种实现路线可选：
- **方案 A**: 自建轻量分层框架，每层做成可插拔接口。
- **方案 B**: 基于 Backtrader（成熟回测框架）做回测引擎，自己写数据适配 + 策略 + CLI 入口。
- **方案 C**: 基于 VectorBT（向量化高速回测），适合大规模参数寻优。

用户的核心诉求是"分析逻辑封装、插件化扩展、支持单股/全市场/手动/定时多种触发"。

## 决策

采用 **方案 A：自建轻量分层框架**。

分层结构（自上而下）：
1. **触发层** (Triggers): CLI / 定时任务 / 未来 Web API。
2. **编排层** (Orchestration): `analyze_stock()` / `run_backtest()` / `analyze_universe()`，不含业务逻辑。
3. **核心引擎层** (Core): DataSource / Indicator / Strategy / Backtester / Reporter，均接口化。

## 理由

1. **契合插件化诉求**: 用户明确要求"数据源、指标、策略都可插拔，指标放目录里可自己加"。自建框架能保证三者风格统一，每层用 ABC 定义接口，新增插件只加文件不改核心。
2. **A 股回测自建成本可控**: T+1、涨跌停、手续费规则明确，撮合逻辑不复杂，无需 Backtrader 那么重的框架。
3. **Backtrader 的不足**: API 重、学习曲线陡，自带一套 Indicator 体系与"插件化指标"理念不完全契合，且近年维护放缓。
4. **VectorBT 的不足**: 偏研究风格（向量化），不适合事件驱动逻辑，与用户"逐股分析封装、可交互触发"的思路不一致。
5. **代码即文档**: 自建框架每个模块职责清晰、可独立测试，长期演进友好。
