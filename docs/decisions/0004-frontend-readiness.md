# ADR-0004: 预留前端对接能力

- 状态: 已接受
- 日期: 2026-06-19
- 决策者: 用户 + ZCode

## 背景

用户在架构选型时补充："自建框架吧，后续可以支持跟前端对接互动"。

这意味着系统不能只服务于 CLI，而要让核心分析逻辑能被未来的 Web API 平等调用。若现在不考虑，未来接前端时需大规模重构。

## 决策

**触发层与核心层完全解耦**，为前端对接预留：

1. **预留 `autotrade/api/` 目录**（MVP 阶段为空占位），明确告知"未来这里是 FastAPI"。
2. **核心编排函数与调用方无关**:
   - `engine.analyze_stock()` / `engine.run_backtest()` 不知道调用方是 CLI / 定时 / HTTP。
   - 三种触发方式最终都调用同一套核心函数，复用率 100%。
3. **CLI 与定时任务共用同一份"命令描述"**: 定时任务的 `command` 字段与 CLI 参数一一对应，未来 Web API 的请求体也用同样语义，保证三种入口参数一致。
4. **FastAPI 依赖声明为 optional**: `pip install autotrade[api]` 才装，MVP 不引入。
5. **配置与代码分离**: 策略参数走 YAML，前端改配置即可调参，无需改代码。

## 理由

1. **避免未来重构**: 现在就把"调用方无关"的边界划清，未来接 FastAPI 只需写一个薄薄的 HTTP 适配层，核心零改动。
2. **职责清晰**: 触发层只做"参数收集 + 调用核心"，绝不掺业务逻辑；这本身也让 CLI/定时更易测试维护。
3. **渐进交付**: MVP 聚焦 CLI + 定时，但架构不堵死 Web 路径，符合"先验证再扩展"的节奏。
4. **前端交互友好**: 报告插件化（console/csv/plot）+ 信号带 `reason` 字段，为前端展示交易解释和图表奠定基础。

## 演进路径

- MVP: CLI + 定时触发，`api/` 目录占位。
- 阶段 2: 实现 `api/main.py`（FastAPI），暴露 `analyze`/`backtest`/`scan` 端点，复用 `engine`。
- 阶段 3: 前端对接（独立项目）。
